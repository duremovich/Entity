3. Catalog: Systems, Components, Archetypes

Now we open the toolbox. Three tables and a recipe-card grid. The systems table is the behavior; the components table is the data; the archetypes are the contracts between them. Every number and path below comes from a live HEAD scan at commit e7fc109 (2026-05-23); see the fact sheet at docs/reference/ for the full methodology. Systems are documented in include/entity/systems/, components in include/entity/components/, and archetypes are defined in docs/reference/ENTITY_ARCHETYPES.md.

Plus an abstract System base class (include/entity/systems/System.hpp) providing the virtual update / initialize / shutdown / getName contract. Not a system in its own right, so not counted above.

Most systems are editor-affinity: the editor thread is the sole registry writer, and systems that write emplace / replace / destroy can only run there. The two exceptions are CompositorSystem and PlaybackPresenter, which are show-affinity and never touch the registry. DecodeSystem and AudioSystem have both: they run on the editor thread in the normal case and fall back to the show thread when the editor is stalled, because they write only atomic fields rather than registry components.

Components (33), grouped

The seven families cluster by purpose. Timeline components hold the raw authoring data for things that live on tracks: start frame, duration, loop mode, decode state, section-break continuation anchor. Animation components encode keyframe tracks and the output of evaluating them, plus the editor viewport camera. Media is thin by design: VideoTexture holds the descriptor-pool slot and the decoded frame pointer; Model holds the GPU mesh. Routing (introduced ADR-0022) is the Plane A content-routing library: named reusable ContentRoutingAsset entities that clips reference via ContentRoutingRef, replacing the old inline ContentRouting component. Output is everything from a physical display to a virtual projector to a stage prop used only for editor pre-visualization. Effects are entities in their own right (per ADR-0019): Effect + EffectParameters sit on separate entities referenced by an EffectChain on the layer. Kind-specific components discriminate generative sub-kinds at the component-composition level rather than at a runtime enum switch.

Note: ContentRoutingAssetOps (include/entity/components/ContentRoutingAssetOps.hpp) is a header of free helper functions for creating, looking up, and applying routing assets. It lives in the components directory for locality but is not a component struct and is never attached to an entity. Do not model it as a component in architecture diagrams.

Archetypes -- what makes a Clip a Clip

EnTT will happily attach any component to any entity; the actual archetypes are conventions enforced by the systems that read them. No archetype is hard-coded at the type-system level. What makes a Clip a Clip is that CompositorSystem, DecodeSystem, and PlaybackTimeAuthority all operate on the combination of Clip + Transform + ClipDecodeState + VideoTexture -- if one of those components is absent, that entity silently falls outside the system's view. The five archetypes below cover roughly 95% of timeline-resident entities on any real show project.

The design principle here is composition-not-inheritance, per ADR-0016 and ADR-0018. Systems select entity kinds by component combination -- view<Layer, Clip> vs. view<Layer, ObjectAnimationLayer> -- never by reading Layer::kind at runtime. The Kind enum on Layer exists for three things only: UI kind badges in the timeline, serialization disambiguation in the project file, and human-readable log output. For the Generative archetype this goes one level deeper: the presence of MunchersGameState versus TextLayerState is the discriminator between the Muncher and Text sub-kinds. There is no sub-kind field to switch on. Adding a new sub-kind means adding a new kind-specific component and wiring it into GenerativeSystem and the compositor's PASS 1 -- PASS 2 doesn't care.

4. The Render Pipeline

Once the editor publishes a bus::SceneSnapshot, the show thread takes over. Everything from here lives on the show thread and writes only to GPU memory -- the registry is read-only on this side, per ADR-0014. The three-pass compositor is specified in docs/adr/0018-content-layer-unification.md (the kind-blind PASS 2 contract) and docs/adr/0019-per-layer-effects.md (the PASS 1.5 ping-pong effect chain). The implementation lives in src/systems/CompositorSystem.cpp and src/render/D3D12Renderer.cpp.

Three passes, kind-blind composite

The compositor's job is to go from a RenderFrame -- a list of ContentLayerSnapshot structs sorted by z-order -- to one filled compose-target texture per visible screen. It does this in three passes.

PASS 1 -- Generative producers. For each active GenerativeLayerSnapshot in the render frame, the compositor calls ensureGenerativeRenderTarget to lazily allocate a compose-target slot (the allocation is confirmed via an R2D GenerativeLayerRenderTargetAllocated ack that the editor writes back to GenerativeLayer::renderTargetSlot on the next editor tick). It then opens that compose target, draws the kind-specific content in layer-local NDC -- the Muncher playfield for Muncher layers, or the texture already rasterized into the video-pool by TextSystem for Text layers -- and closes the target. Output: one compose-target texture per active generative layer. Video clips do not go through PASS 1; their textures are already in the video-pool, uploaded by PlaybackPresenter::present() before the compositor runs.

PASS 1.5 -- Per-layer effect chains. For each ContentLayerSnapshot whose effects list is non-empty, the compositor ensures two ping-pong compose targets exist (EffectChainRenderTargets, again via R2D ack). It then walks the effect chain, calling drawEffectPass per enabled Effect, ping-ponging input and output targets each pass. The final result lands in postEffectsSlot on the layer snapshot. The kind-blind contract here is strict: PASS 1.5 operates identically on Video-sourced layers and Compose-sourced (generative) layers. It doesn't care what produced the source texture. PASS 1.5 is a complete no-op for layers with empty effect chains -- no targets are allocated and no draw calls are issued.

PASS 2 -- Unified composite per screen. For each visible screen, the compositor calls ensureScreenRenderTarget (R2D ack writes Screen::renderTargetSlot on the editor thread) and opens the screen's compose target. It then walks every ContentLayerSnapshot in rf.contentLayers -- already sorted by zOrder -- that is targeted at this screen, and calls drawTexturedQuad per layer. When a layer has postEffectsSlot >= 0, PASS 2 reads from the effect-chain output instead of sourceSlot. The source-kind enum dispatches the descriptor pool: Video reads from the video-texture pool; Compose reads from the generative-layer RT pool. One PASS 2 implementation handles every content kind that exists today or will exist tomorrow.

This is the payoff of ADR-0018. Adding a new content-producing layer kind -- a Particle layer, a Shader layer, anything -- requires PASS 1 work to produce a texture in a compose-target slot, but PASS 2 does not change. The compositor is closed for modification, open for extension on the consumer side.

Source: ADR-0018 + ADR-0019. Implemented in src/systems/CompositorSystem.cpp + src/render/D3D12Renderer.cpp.

The descriptor heap -- where every texture lives

The show pipeline uses a single CBV/SRV/UAV descriptor heap allocated at startup. Slot ranges are fixed and collision-free since CRIT-04 was resolved in Phase A (2026-04-19). The layout groups resources by role so that each system can compute its slot from a base constant plus an index without coordinating with any other system at runtime. The slot constants live in include/entity/render/D3D12Renderer.hpp.

Slot 0 holds the ImGui font atlas SRV. Slot 1 is a legacy video upload slot retained for the transitional code path. The compose-target range starts at COMPOSE_TARGET_BASE = 2 and spans 64 slots -- this covers screen render targets, generative-layer render targets, and the ping-pong pairs allocated by PASS 1.5 effect chains. The video-texture pool starts at VIDEO_TEXTURE_BASE = 66 and provides 16 slots, one per active decoded clip -- PlaybackPresenter uploads each decoded frame here before the compositor runs. Above that, SNAPSHOT_BASE = 82 marks the start of the per-frame constant buffer ring (64 CBV slots of 256 bytes each, one per frame-in-flight slot), which is what fixed the CRIT-04 multi-surface overwrite.

Output stage -- from screen RT to projector pixel

After PASS 2 finishes, each visible Screen has a filled compose target in the descriptor heap. OutputManager::renderOutputs() walks every enabled OutputDisplay entity and drives it to its swap chain.

For each OutputDisplay: the manager looks up the bound screen (via sourceScreen) or the bound projector (via sourceProjector, which takes priority). It reads the screen's renderTargetSlot -- the compose-target index assigned by CompositorSystem via the R2D ack. It then walks every visible OutputSurface for that output -- these are the Plane B warp quads per ADR-0021, renamed from MappingSurface in ADR-0021 M4 -- and for each quad draws a warped blit: source UV from InputRegion, destination from the quad's four corner positions, with soft-edge feathering at the quad margins.

When the output is bound through a Projector rather than a flat screen, an additional calibration pass applies before the warp. The calibration math per ADR-0011 (docs/adr/0011-projector-calibration-architecture.md) is a four-step pipeline: (1) intrinsic matrix (fx, fy, cx, cy) maps the screen to the projector's image plane; (2) extrinsic R|t is solved via Levenberg-Marquardt over the operator's correspondence point pairs; (3) radial distortion k1 and k2 correct lens barrel/pincushion; (4) an IDW (inverse-distance weighted) residual warp grid corrects whatever the analytic model misses. ADR-0011 flags five coupled sites in the codebase that must move together when this math changes -- touch them as a unit or the calibration will silently break.

After the warp, an OCIO color transform is applied per-output before Present(). The swap chains use DXGI_SWAP_EFFECT_FLIP_DISCARD.

Plane A vs. Plane B -- don't conflate them. OutputSurface (renamed from MappingSurface in ADR-0021 M4) is a per-output warp quad -- Plane B. It describes how a screen's render target is physically deformed onto the projection surface. ContentRoutingAsset (ADR-0022) routes layer content to screens -- Plane A. It describes which clip goes where in logical screen space. The two planes are completely independent: a single screen can have many clips routed to it (Plane A), and that screen's render target can be warped by many output surfaces across many physical displays (Plane B).

Triple-buffered everything

The show pipeline uses D3D12 per-frame command allocators. m_showAllocators is an array indexed by frame-in-flight slot; m_showFence gates the CPU from reusing a slot before the GPU has finished with it. beginShowFrame resets the allocator for the current slot, opens the command list, and opens a Tracy GPU zone (a cross-function zone -- the tracy::D3D12ZoneScope* lives on the heap, allocated in beginShowFrame and deleted at the very top of endShowFrame before any early returns, per ADR-0015). endShowFrame closes the Tracy zone, executes the command list, and Presents all enabled output swap chains.

Compose targets follow the same discipline. Each target has a lastStableIndex that is acquire/release-fenced so the editor never reads a render target slot the show thread is currently writing into. This is particularly relevant for Screen::renderTargetSlot -- the slot is written on the editor thread (via the R2D ack drain in drainRendererToDirector) and read on the show thread in ensureScreenRenderTarget.

The editor and show threads share one D3D12 direct command queue. The D3D12 specification guarantees that ExecuteCommandLists and Signal are thread-safe on a single queue object -- that guarantee is the contract the editor/show split relies on. Both threads submit independently; the fence values keep them from stepping on each other's in-flight work.
