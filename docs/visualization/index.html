Entity Media Server

Architecture overview · generated 2026-05-23 at e7fc109

1. Project at a Glance

Entity is a C++20 media server for live projection mapping. The engine is built around an Entity Component System (EnTT 3.x), a D3D12 renderer, and an FFmpeg decode pipeline. A single editor executable hosts both the authoring UI (ImGui, D3D12 swap chain) and the projector output pipeline (a parallel show thread that keeps GPU presents running at 60 Hz even while the editor blocks). The codebase is dual-licensed open-core: a GPLv3 core with an Apache 2.0 plugin layer, plus a sibling private repository (Entity-Pro) that folds in via -DEXTRA_PLUGIN_DIRS.

The product context is live shows -- theater, concerts, installations, immersive experiences -- where one or more projectors throw video onto irregular surfaces (LED walls, stage props, building facades) and need to do so at frame-accurate 60 Hz while an operator authors cues, calibrates surfaces, and triggers transitions live. That use case sets every architectural constraint: the projector output is sacred and must never freeze; clips need frame-accurate seek without an audible glitch; the editor must stay responsive even when loading 4K ProRes off disk. Most of what follows is downstream of those constraints.

2. The Architecture Spine

ECS + Data-Oriented Design -- the substrate

Every piece of runtime state in Entity lives on one of three primitives: an entity (just an integer ID -- no data, no behavior), a component (a plain data struct attached to an entity), or a system (a class that reads and writes components in bulk via registry.view<Components...>()). EnTT's sparse-set storage packs components contiguously in memory, so iterating a view is a sequential walk through dense arrays rather than a pointer chase.

That layout buys three properties that matter in a realtime media server:

  • Cache coherency. When CompositorSystem iterates view<Transform, MediaLayer>(), both component arrays march through cache lines together. Putting logic or vtables inside components would fragment those arrays and turn a predictable sequential read into a random walk.
  • Threading discipline. Components are value types -- they are cheap to copy and snapshot-bake across threads. The editor/show split (below) works only because there are no embedded mutexes, no internal thread state, no reference-counted shared ownership to reason about.
  • Inspectability. Pure data is easy to print, diff, and serialize. The project's multi-version project file (schema v1 to v22+) and the bus::SceneSnapshot snapshot wire format both benefit directly from components being flat structs.

Documented component exceptions. Three components carry methods that would violate strict POD purity -- all three are explicitly reviewed and acceptable under the rule: a method is fine if it has no virtuals, touches only the component's own fields, and adds no construction/destruction cost.

  • Clip -- has a destructor and move-only semantics that free its FFmpeg AVFormatContext / AVCodecContext. RAII is safer than a scattered "don't forget to call close()" contract. This is the only component in the tree that owns heap resources.
  • Transform -- has updateMatrix() / setPosition() / getMatrix() etc. that cache a dirty-flag matrix from the component's own position/rotation/scale fields. No virtuals, no cross-component reach.
  • AnimatedProperties / KeyframeTrack -- have addKeyframe() / evaluate() that operate only on their own track data. Cache-local, no virtuals, no external state.

Everything that does reach outside a component -- input handling, multi-component side effects, cross-system coordination -- lives in a system. The base class include/entity/systems/System.hpp has virtuals (update, initialize, shutdown, getName) which is fine because systems are not iterated in packed arrays; one indirect call per system per frame is trivial cost.

The editor/show thread split

The single most important architectural decision in Entity is that the editor thread is the sole writer of the EnTT registry. Everything that reads from the registry for rendering does so through a baked snapshot, never through a live registry read. This is the subject of docs/adr/0014-editor-show-thread-split.md.

The editor thread (Engine::update, ~60 Hz) is responsible for all registry mutations. Its per-frame order is:

  1. Time advance -- Timeline::update(dt) writes the atomic m_currentTime.
  2. Section scheduling -- SectionScheduler::tick() applies catch-up continuation phase; break-crossing detection now runs on the show thread (see below).
  3. Animation -- AnimationSystem::update(dt) evaluates keyframe tracks and writes Transform + ObjectAnimationOutput registry components.
  4. Text rasterization -- TextSystem::update() rasterizes dirty TextLayerState entries to video-pool textures via DirectWrite + D2D.
  5. Content scanner -- drainContentScannerDeltas() folds filesystem-watcher deltas into the media bin.
  6. Decode steering -- DecodeSystem::update() maps the current timeline frame to a media frame for each clip and writes the atomic worker->targetFrame.
  7. Audio steering -- AudioSystem::update() manages AudioDecodeWorker threads; mirrors gain/mute/solo to the mixer.
  8. Seek sync -- SeekSyncController::tick() polls decoder readiness and releases the seek-sync gate when all active decoders reach the parked frame.
  9. Heartbeat -- m_lastEditorTickNs.store(now) so the show thread can detect editor stalls.
  10. UI -- ImGui new-frame plus all editor window rendering. Writes go through CommandDispatcher.
  11. Command drain -- CommandDispatcher::processQueue(Editor + Either affinity) applies all pending commands; this is the only other registry-write site.
  12. Snapshot -- buildSceneSnapshot() bakes the registry into a bus::SceneSnapshot and publishes it onto the D2R bus.
  13. Reply drain -- drainRendererToDirector() reads R2D replies (for example, ScreenRenderTargetAllocated -- the compose-target slot ack -- triggers a registry write of Screen::renderTargetSlot).
  14. Present -- beginEditorFrame / endEditorFrame for the editor swap chain.

The show thread (Engine::showThreadMain, 60 Hz output framerate) never writes the registry. Its per-frame order is:

  1. Time advance -- Timeline::update(dt) unconditionally advances m_currentTime every show frame, decoupled from editor health.
  2. Section break detection -- the SectionDetect Tracy zone finds any break-frame the playhead just crossed, snaps and pauses the playhead, and posts an R2D bus::SectionBreakDetected. No registry writes.
  3. Editor-stall fallback -- if the editor heartbeat is stale by more than 50 ms, the show thread calls DecodeSystem::update() and AudioSystem::update() directly.
  4. Command drain -- CommandDispatcher::processQueue(Show affinity) drains Play / Pause / Seek / SectionGo; writes only atomics on Timeline, never the registry.
  5. Snapshot drain -- pull the latest SceneSnapshot from the D2R bus (latest-wins delivery; superseded snapshots are discarded).
  6. GPU upload -- PlaybackPresenter::present() uploads decoded frames from FrameRingBuffer to GPU textures.
  7. Composite -- CompositorSystem::update(renderFrame), three passes (see S4 for detail).
  8. Output -- OutputManager::renderOutputs() fans each screen's compose target to its assigned output swap chain.
  9. Present -- endShowFrame closes the Tracy D3D12 zone, executes the command list, and calls Present() on all output swap chains.

The bus. D2R (Director-to-Renderer) carries the bus::SceneSnapshot with latest-wins delivery -- if the editor publishes two snapshots before the show thread drains one, the older snapshot is silently superseded. R2D (Renderer-to-Director) is FIFO and carries reply messages: compose-target slot acks (ScreenRenderTargetAllocated, GenerativeLayerRenderTargetAllocated), effect-chain slot acks (EffectChainRenderTargetAllocated), and section-break crossing events (SectionBreakDetected). Decode / transcode / scanner / plugin workers are independent of both threads -- they write atomics that the editor reads each tick.

Editor-stall fallbacks -- keeping the projector alive

When the editor thread blocks for more than ~50 ms -- a native file-picker dialog, an OS resize/move loop, a slow project load -- Engine::update stops running. Every editor-tick system stops with it. Without a counter-measure, the projector output freezes on whatever frame the user last saw. In a live show, that is a failure.

The show thread polls m_lastEditorTickNs (the heartbeat written at editor step 6) to detect staleness. Two counter-measure shapes cover all the systems that matter:

  • Show-fallback tick. When the system's per-frame work writes only atomics and never the registry, the show thread can call the system's update() directly on the stall path. Systems using this shape:
    • Timeline -- m_currentTime is an atomic; the show thread has called Timeline::update(dt) unconditionally since commit ee99a99, not just during editor stalls.
    • DecodeSystem -- writes only the atomic worker->targetFrame; the show-thread fallback has been in place since commit a9bcd8b.
    • AudioSystem -- writes only atomic worker fields (seekTarget, active) and MixSource mixer-slot fields; fallback fires on the same 50 ms heartbeat gate as DecodeSystem.
  • Snapshot-bake and re-derive. When the system writes registry components, the show thread cannot call it at all. Instead, the editor bakes the system's output into bus::SceneSnapshot::clipCatalog once per editor frame, and the show thread re-evaluates from those baked inputs each render frame in buildRenderFrame(). Systems using this shape:
    • AnimationSystem (NEW-07, closed 2026-05-11). Keyframe tracks for each clip are baked into bus::ClipCatalogEntry. The show thread re-evaluates them in buildRenderFrame, overriding ClipRenderState::transformMatrix / opacity for animated clips. Design doc: docs/design/animation-snapshot-bake.md.
    • SectionScheduler (NEW-08, closed 2026-05-20). Because SectionScheduler is a state machine -- not a stateless evaluator like AnimationSystem -- snapshot-bake alone is not sufficient. The solution splits the work: break-crossing detection runs on the show thread (the SectionDetect zone, step 1.1); the registry-mutating application (SectionScheduler::handleBreakAt) stays on the editor thread, triggered by an R2D bus::SectionBreakDetected message drain. Continuation phase is re-derived show-side from a wall-clock anchor baked into ClipCatalogEntry fields (phase_continuationStartTimeNs / phase_continuationSeedFrames), so Loop and PingPong clips keep cycling at a parked break even during a multi-second editor stall. Design doc: docs/design/section-scheduler-snapshot-bake.md.

TextSystem does not need either mechanism. Text content only changes on explicit authoring commands -- it does not advance with wall time. The last-baked texture remains valid at the GPU indefinitely during a stall.

Diagnostic recipe: "is the output frozen?" Before chasing display-layer theories (DWM composition, Independent Flip, swap-chain fullscreen mode, driver bugs), add ~20 lines to render an independent per-frame counter quad to the output -- a small color-cycling square in a corner that is totally independent of Timeline, SceneSnapshot, and decode state. Then trigger the suspected stall and observe:

  • Counter keeps cycling -- the swap chain is fine. The freeze is in the content pipeline: some editor-tick system stopped feeding the show thread. Check whether it has a show-thread fallback per docs/adr/0014-editor-show-thread-split.md.
  • Counter freezes too -- the freeze really is in the swap chain or display path. Use PresentMon to confirm whether the OS is completing your presents. Genuinely rare on this codebase given the editor/show split.

This recipe was learned the hard way (commit a9bcd8b): ~6 hours of display-layer investigation before the marker test pivoted to the actual six-line content-pipeline fix.

The fallback coverage is now complete. There are no known editor-stall gaps -- NEW-07 (AnimationSystem) closed 2026-05-11 and NEW-08 (SectionScheduler) closed 2026-05-20 were the last two. Any new editor-tick system that drives the projector output must choose one of these two shapes before shipping: show-fallback tick (if registry-write-free) or snapshot-bake (if it writes registry components). The checklist is in docs/adr/0014-editor-show-thread-split.md under "Show-Thread Fallback Pattern."

With the spine established -- two threads, one registry, one baked snapshot, two fallback shapes -- the next three sections walk down it. S3 inventories what is actually inside the components and systems. S4 follows the render path from snapshot drain through the three-pass compositor to the output swap chains. S5 catalogs the 22 editor windows and the command loop that connects operator input back to registry state.

Components (33), grouped

The seven families cluster by purpose. Timeline components hold the raw authoring data for things that live on tracks: start frame, duration, loop mode, decode state, section-break continuation anchor. Animation components encode keyframe tracks and the output of evaluating them, plus the editor viewport camera. Media is thin by design: VideoTexture holds the descriptor-pool slot and the decoded frame pointer; Model holds the GPU mesh. Routing (introduced ADR-0022) is the Plane A content-routing library: named reusable ContentRoutingAsset entities that clips reference via ContentRoutingRef, replacing the old inline ContentRouting component. Output is everything from a physical display to a virtual projector to a stage prop used only for editor pre-visualization. Effects are entities in their own right (per ADR-0019): Effect + EffectParameters sit on separate entities referenced by an EffectChain on the layer. Kind-specific components discriminate generative sub-kinds at the component-composition level rather than at a runtime enum switch.

Note: ContentRoutingAssetOps (include/entity/components/ContentRoutingAssetOps.hpp) is a header of free helper functions for creating, looking up, and applying routing assets. It lives in the components directory for locality but is not a component struct and is never attached to an entity. Do not model it as a component in architecture diagrams.

Archetypes -- what makes a Clip a Clip

EnTT will happily attach any component to any entity; the actual archetypes are conventions enforced by the systems that read them. No archetype is hard-coded at the type-system level. What makes a Clip a Clip is that CompositorSystem, DecodeSystem, and PlaybackTimeAuthority all operate on the combination of Clip + Transform + ClipDecodeState + VideoTexture -- if one of those components is absent, that entity silently falls outside the system's view. The five archetypes below cover roughly 95% of timeline-resident entities on any real show project.

The design principle here is composition-not-inheritance, per ADR-0016 and ADR-0018. Systems select entity kinds by component combination -- view<Layer, Clip> vs. view<Layer, ObjectAnimationLayer> -- never by reading Layer::kind at runtime. The Kind enum on Layer exists for three things only: UI kind badges in the timeline, serialization disambiguation in the project file, and human-readable log output. For the Generative archetype this goes one level deeper: the presence of MunchersGameState versus TextLayerState is the discriminator between the Muncher and Text sub-kinds. There is no sub-kind field to switch on. Adding a new sub-kind means adding a new kind-specific component and wiring it into GenerativeSystem and the compositor's PASS 1 -- PASS 2 doesn't care.

4. The Render Pipeline

Once the editor publishes a bus::SceneSnapshot, the show thread takes over. Everything from here lives on the show thread and writes only to GPU memory -- the registry is read-only on this side, per ADR-0014. The three-pass compositor is specified in docs/adr/0018-content-layer-unification.md (the kind-blind PASS 2 contract) and docs/adr/0019-per-layer-effects.md (the PASS 1.5 ping-pong effect chain). The implementation lives in src/systems/CompositorSystem.cpp and src/render/D3D12Renderer.cpp.

Three passes, kind-blind composite

The unifying abstraction the compositor works on is the content layer: a video clip, a generative layer (Muncher, Text), or any future kind that produces a texture for a screen. Each one contributes one ContentLayerSnapshot to the render frame, and from PASS 1.5 onward the pipeline is kind-blind -- it doesn't matter what produced the texture, only that there is one. This is the payoff of ADR-0018; adding a new layer kind means writing PASS 1 producer code, and nothing else changes.

The compositor's job is to go from a RenderFrame -- a list of ContentLayerSnapshot structs sorted by z-order -- to one filled compose-target texture per visible screen. It does this in three passes.

PASS 1 -- Generative producers. For each active GenerativeLayerSnapshot in the render frame, the compositor calls ensureGenerativeRenderTarget to lazily allocate a compose-target slot (the allocation is confirmed via an R2D GenerativeLayerRenderTargetAllocated ack that the editor writes back to GenerativeLayer::renderTargetSlot on the next editor tick). It then opens that compose target, draws the kind-specific content in layer-local NDC -- the Muncher playfield for Muncher layers, or the texture already rasterized into the video-pool by TextSystem for Text layers -- and closes the target. Output: one compose-target texture per active generative layer. Video clips do not go through PASS 1; their textures are already in the video-pool, uploaded by PlaybackPresenter::present() before the compositor runs.

PASS 1.5 -- Per-layer effect chains. For each ContentLayerSnapshot whose effects list is non-empty, the compositor ensures two ping-pong compose targets exist (EffectChainRenderTargets, again via R2D ack). It then walks the effect chain, calling drawEffectPass per enabled Effect, ping-ponging input and output targets each pass. The final result lands in postEffectsSlot on the layer snapshot. The kind-blind contract here is strict: PASS 1.5 operates identically on Video-sourced layers and Compose-sourced (generative) layers. It doesn't care what produced the source texture. PASS 1.5 is a complete no-op for layers with empty effect chains -- no targets are allocated and no draw calls are issued.

PASS 2 -- Unified composite per screen. For each visible screen, the compositor calls ensureScreenRenderTarget (R2D ack writes Screen::renderTargetSlot on the editor thread) and opens the screen's compose target. It then walks every ContentLayerSnapshot in rf.contentLayers -- already sorted by zOrder -- that is targeted at this screen, and calls drawTexturedQuad per layer. When a layer has postEffectsSlot >= 0, PASS 2 reads from the effect-chain output instead of sourceSlot. The source-kind enum dispatches the descriptor pool: Video reads from the video-texture pool; Compose reads from the generative-layer RT pool. One PASS 2 implementation handles every content kind that exists today or will exist tomorrow.

This is the payoff of ADR-0018. Adding a new content-producing layer kind -- a Particle layer, a Shader layer, anything -- requires PASS 1 work to produce a texture in a compose-target slot, but PASS 2 does not change. The compositor is closed for modification, open for extension on the consumer side.

Source: ADR-0018 + ADR-0019. Implemented in src/systems/CompositorSystem.cpp + src/render/D3D12Renderer.cpp.

The descriptor heap -- where every texture lives

The show pipeline uses a single CBV/SRV/UAV descriptor heap allocated at startup. Slot ranges are fixed and collision-free since CRIT-04 was resolved in Phase A (2026-04-19). The layout groups resources by role so that each system can compute its slot from a base constant plus an index without coordinating with any other system at runtime. The slot constants live in include/entity/render/D3D12Renderer.hpp.

Slot 0 holds the ImGui font atlas SRV. Slot 1 is a legacy video upload slot retained for the transitional code path. The compose-target range starts at COMPOSE_TARGET_BASE = 2 and spans 64 slots -- this covers screen render targets, generative-layer render targets, and the ping-pong pairs allocated by PASS 1.5 effect chains. The video-texture pool starts at VIDEO_TEXTURE_BASE = 66 and provides 16 slots, one per active decoded clip -- PlaybackPresenter uploads each decoded frame here before the compositor runs. Above that, SNAPSHOT_BASE = 82 marks the start of the per-frame constant buffer ring (64 CBV slots of 256 bytes each, one per frame-in-flight slot), which is what fixed the CRIT-04 multi-surface overwrite.

Output stage -- from screen RT to projector pixel

After PASS 2 finishes, each visible Screen has a filled compose target in the descriptor heap. OutputManager::renderOutputs() walks every enabled OutputDisplay entity and drives it to its swap chain.

For each OutputDisplay: the manager looks up the bound screen (via sourceScreen) or the bound projector (via sourceProjector, which takes priority). It reads the screen's renderTargetSlot -- the compose-target index assigned by CompositorSystem via the R2D ack. It then walks every visible OutputSurface for that output -- these are the Plane B warp quads per ADR-0021, renamed from MappingSurface in ADR-0021 M4 -- and for each quad draws a warped blit: source UV from InputRegion, destination from the quad's four corner positions, with soft-edge feathering at the quad margins.

When the output is bound through a Projector rather than a flat screen, an additional calibration pass applies before the warp. The calibration math per ADR-0011 (docs/adr/0011-projector-calibration-architecture.md) is a four-step pipeline: (1) intrinsic matrix (fx, fy, cx, cy) maps the screen to the projector's image plane; (2) extrinsic R|t is solved via Levenberg-Marquardt over the operator's correspondence point pairs; (3) radial distortion k1 and k2 correct lens barrel/pincushion; (4) an IDW (inverse-distance weighted) residual warp grid corrects whatever the analytic model misses. ADR-0011 flags five coupled sites in the codebase that must move together when this math changes -- touch them as a unit or the calibration will silently break.

After the warp, an OCIO color transform is applied per-output before Present(). The swap chains use DXGI_SWAP_EFFECT_FLIP_DISCARD.

Plane A vs. Plane B -- don't conflate them. OutputSurface (renamed from MappingSurface in ADR-0021 M4) is a per-output warp quad -- Plane B. It describes how a screen's render target is physically deformed onto the projection surface. ContentRoutingAsset (ADR-0022) routes layer content to screens -- Plane A. It describes which clip goes where in logical screen space. The two planes are completely independent: a single screen can have many clips routed to it (Plane A), and that screen's render target can be warped by many output surfaces across many physical displays (Plane B).

Triple-buffered everything

The show pipeline uses D3D12 per-frame command allocators. m_showAllocators is an array indexed by frame-in-flight slot; m_showFence gates the CPU from reusing a slot before the GPU has finished with it. beginShowFrame resets the allocator for the current slot, opens the command list, and opens a Tracy GPU zone (a cross-function zone -- the tracy::D3D12ZoneScope* lives on the heap, allocated in beginShowFrame and deleted at the very top of endShowFrame before any early returns, per ADR-0015). endShowFrame closes the Tracy zone, executes the command list, and Presents all enabled output swap chains.

Compose targets follow the same discipline. Each target has a lastStableIndex that is acquire/release-fenced so the editor never reads a render target slot the show thread is currently writing into. This is particularly relevant for Screen::renderTargetSlot -- the slot is written on the editor thread (via the R2D ack drain in drainRendererToDirector) and read on the show thread in ensureScreenRenderTarget.

The editor and show threads share one D3D12 direct command queue. The D3D12 specification guarantees that ExecuteCommandLists and Signal are thread-safe on a single queue object -- that guarantee is the contract the editor/show split relies on. Both threads submit independently; the fence values keep them from stepping on each other's in-flight work.

Closing

That's the pipeline. A SceneSnapshot goes in; projector pixels come out, sixty times per second, regardless of what the editor thread is doing. The next section walks the surface the operator actually clicks on -- the 22 ImGui windows that decide what the next SceneSnapshot will contain.

5. The Editor Surface

Twenty-two files in src/ui/ decide what the next bus::SceneSnapshot will look like. Each window holds a Director* pointer and reads registry components directly for display — but it writes only through CommandDispatcher. Every mutation is an undoable command with editor-thread affinity. This discipline is what lets the editor thread remain the sole registry writer per docs/adr/0014-editor-show-thread-split.md: there is no back-channel, no direct registry call from a UI event handler. The command is enqueued, the dispatcher executes it at editor-thread step 8 (CommandDispatcher::processQueue(Editor | Either) per docs/reference/SYSTEM_ORDERING.md), and the registry write happens exactly once, in the right thread, at the right moment.

Authoring loop — how a window mutation reaches the projector

Tracing one concrete action — the operator clicks "Add Effect" in PropertyWindow:

  1. PropertyWindow calls CommandDispatcher::enqueue with an AddEffectCommand.
  2. Editor-thread step 8 executes the command. The registry write happens here: EffectChain and Effect components are emplaced.
  3. Editor-thread step 9 (buildSceneSnapshot) bakes the new effect into bus::SceneSnapshot::layerEffects.
  4. The snapshot publishes to the D2R bus. The show thread drains it on the next show frame.
  5. The show thread's PASS 1.5 sees a non-empty effect chain and allocates ping-pong render targets, posting an R2D EffectChainRenderTargetAllocated reply.
  6. Editor-thread step 10 drains the R2D bus and writes the allocated slot IDs back to EffectChainRenderTargets on the registry.
  7. The next buildSceneSnapshot bakes those slot IDs. The show thread renders the effect starting that frame.

Every UI action takes 1–2 frames to reach the projector. That is the bus-roundtrip cost the architecture pays for the thread-isolation guarantee. On a 60 Hz show thread it is under 34 ms — imperceptible in practice, and worth every microsecond given what it buys.

Project on disk

A project is a folder, not a single file. ShowName.entity is the JSON manifest inside the folder; content/ holds all media and is auto-discovered by ContentScanner (filesystem watcher). Transcodes overwrite originals at the canonical path; pre-transcode originals are archived in per-folder .archive/ sibling directories under content/ as the fallback if a transcode goes wrong (per docs/adr/0010-structured-project-layout.md). presets/ and objects/ are user assets. snapshots/ and exports/ are output artifacts. .cache/ is machine-local and regenerable — it does not travel with the project and is excluded from rsync or bundle operations. The content/ tree uses Managed (project-relative) or Linked (absolute path) path kinds, giving flexibility for large networked media libraries.

6. Plugin Layer & License Seam

Entity ships as open-core. The public repo at C:\Entity\Entity carries a GPLv3 core plus an Apache-2.0 plugin layer. A sibling private repo at C:\Entity\Entity-Pro holds proprietary Pro plugins that fold into the public build at CMake configure time via the -DEXTRA_PLUGIN_DIRS flag. This section explains where the seam is, what crosses it legally, and what does not. Note: C:\Entity\Entity-Pro is not present on this machine — the architecture is fully documented and the public build supports it, but Pro plugin source content is on a separate machine.

Two plugin transport tiers

Per docs/adr/0005-open-core-dual-license.md, plugins fall into two tiers based on their data path:

  • Control-plane plugins communicate via IPluginContext::enqueueCommand() (per docs/adr/0013-control-plane-plugins-route-via-command-dispatcher.md) or via OutboundBridge::emit() for emitting engine state outbound (per docs/adr/0023-control-plane-plugin-outbound-bridge.md). These plugins handle OSC, DMX, timecode, and telemetry — anything network-serializable. The entity-bus itself stays Director-to-Renderer only. Future upgrade from static to dynamic plugin loading is purely additive for this tier.
  • Hot-path plugins implement the OutputDriver or CodecProvider C++ ABIs defined in plugin-api/include/entity/plugin/. Static-link only; toolchain-locked. These would handle per-frame GPU data paths: NDI/SDI output drivers, custom codec providers, custom shader passes.

No public hot-path plugins exist today. All four first-party plugins (bus-logger, osc-receiver, osc-sender, dmx-artnet) are control-plane. The hot-path ABI is defined in plugin-api/include/entity/plugin/ and ready for plugins, but the public repo has none. NDI output drivers, SDI providers, and Decklink-internal integrations would be hot-path candidates when they land.

Repo split and license map

The public repo at C:\Entity\Entity contains three internal license regions. The GPLv3 core (with a linking exception) covers everything in src/ and include/entity/ except the plugin-api headers and the bus. The linking exception is what makes proprietary plugins legal: they may link against the core without inheriting the GPL. The Apache 2.0 region covers entity-bus/, plugin-api/, and plugins/ (the first-party plugin implementations). A single root-level file (LICENSE-PLUGIN-API) covers all of it. The plugin-api/ headers are forbidden from including <entt/entt.hpp> or <d3d12.h> or reaching into engine internals — CI enforces this boundary. That isolation is the legal seam. License files at repo root: LICENSE, LICENSE-PLUGIN-API, LICENSING.md, THIRD_PARTY_LICENSES.md.

The private Entity-Pro sibling repo has no CMakeLists.txt at its own root. The public build folds it in via -DEXTRA_PLUGIN_DIRS=C:/Entity/Entity-Pro/plugins, wired at CMakeLists.txt lines 363–375. CI never references the Pro repo. Pro plugin contents stay proprietary; the public build simply excludes them when the flag is not passed.

The open-core principle, briefly

Per docs/adr/0007-open-core-feature-tiering.md: gate Pro features by capability, not by capacity or watermark. Public Entity is fully functional for single-machine show work. There are no nag screens, no time-limited trial mode, no watermarked output. You can run a real show on the open-core build.

Pro adds capabilities that the open core cannot offer cleanly given its scope: cluster sync across multiple machines, proprietary vendor SDK integrations (Decklink-internal, Notch, Quadro Sync II), and deeper show-control integrations. The principle keeps the public version genuinely useful while making the Pro purchase a clean capability upgrade rather than the unlocking of an artificial restriction.

The fact that Pro features land as plugins by default — rather than as #ifdef blocks in the core — is itself a structural consequence of the open-core model. The plugin layer is the right place for them, and it keeps the core reviewable.

The plugin layer is the extension surface. If a feature can be plugin-shaped, it should be — even Pro features default to plugins. The C++ ABI at plugin-api/include/entity/plugin/ is the tight contract for hot-path plugins; the IPluginContext::enqueueCommand path is the looser one for control-plane plugins. Both are stable surfaces. Adding a new plugin means copying from plugins/bus-logger/ — the scaffold template exists precisely for this.
